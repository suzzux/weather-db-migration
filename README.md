# Лабораторна робота: Міграція Бази Даних

## Відповіді на контрольні питання

### 1\. Чи можна завантажувати всю базу, а описувати в ORM моделі тільки деякі колонки?

**Відповідь:** Так, абсолютно. ORM-модель (SQLAlchemy) не зобов'язана відображати всі стовпці таблиці в базі даних або всі стовпці вихідного CSV-файлу:

- **На рівні читання з файлу:** При парсингу вихідного CSV-файлу ми зчитуємо всі поля рядка, але створюємо екземпляр ORM-моделі (`WeatherReport`), передаючи значення лише для тих колонок, які нас цікавлять. Усі інші поля файлу просто ігноруються.  
- **На рівні бази даних:** Якщо в реальній таблиці бази даних існують інші стовпці, не описані в класі SQLAlchemy, це не викликає помилок. Під час виконання запитів (`SELECT`, `INSERT`) ORM формує SQL-запити, які оперують виключно полями, явно визначеними в моделі. Неописані стовпці залишаються незачепленими.

### 2\. Чи є дефолтне значення при створенні у колонці «Чи варто виходити на вулицю»? Поясніть?

**Відповідь:**

- **На рівні бізнес-логіки застосунку:** Фіксованого статичного дефолтного значення (наприклад, просто `True` чи `False`) бути не повинно, тому що це динамічно обчислювана оцінка, яка залежить від конкретних погодних параметрів (індексу якості повітря US EPA, концентрації дрібнодисперсного пилу PM2.5 та чадного газу CO).  
- **На рівні схеми бази даних при додаванні колонки:** Оскільки колонка додається до таблиці, яка **вже містить існуючі записи**, СУБД вимагає або наявності дефолтного значення (`server_default`), або дозволу на `NULL`.

### 3. У скільки етапів ви зробили 3-тє завдання?
**Відповідь:**
Третє завдання (додавання булевої колонки `should_go_outside` з обмеженням `NOT NULL` без втрати та спотворення даних) було реалізовано у **3 етапи** в межах міграції Alembic:

1. **Етап 1:** Додавання нової колонки `should_go_outside` типу `Boolean` з дозволом значень `NULL` (`nullable=True`), щоб база даних могла успішно додати стовпець до вже заповненої таблиці.
2. **Етап 2 (Data Migration):** Оновлення всіх існуючих записів у таблиці за допомогою SQL-запиту з обчисленням умови:
   ```sql
   UPDATE air_quality 
   SET should_go_outside = CASE 
       WHEN us_epa_index <= 2 AND pm2_5 < 35.0 THEN TRUE 
       ELSE FALSE 
   END;
   ```
3. **Етап 3:** Зміна властивостей колонки на `nullable=False` (`ALTER COLUMN ... SET NOT NULL`), що гарантує цілісність даних для всіх наступних операцій запису.

### 4\. На яку частину застосунку ви поклали функцію заповнення колонки «Чи варто виходити на вулицю» даними?

**Відповідь:** Відповідальність розділено між двома шарами залежно від типу операції:

1. **Для нових даних (імпорт або додавання через програму):** Функцію розрахунку покладено на **Шар бізнес-логіки (Service Layer — клас `WeatherService`)**. Метод `calculate_should_go_outside()` оцінює стан повітря перед збереженням і передає готове значення до Data Access Layer (`WeatherRepository`). Це відповідає принципам чистої Layered Architecture, оскільки бізнес-правила не повинні знаходитися в моделях або контролерах.  
2. **Для історичних даних, які вже зберігалися в базі під час рефакторингу:** Функцію заповнення покладено на **скрипт міграції Alembic (Migration Script)**, який безпосередньо в базі даних за допомогою SQL-виразу `UPDATE` виконав розрахунок для наявних рядків без перевантаження даних у застосунок.

### 5\. Чи легко було накочувати міграції, перейти з однієї бази на іншу? Які проблеми траплялись?

**Відповідь:** Завдяки абстракції SQLAlchemy та версіонуванню Alembic міграції накочувалися прозоро, а для зміни СУБД з PostgreSQL на MySQL було достатньо змінити рядок підключення (`DATABASE_URL`).

Проте під час переходу та налаштування виникли характерні особливості та труднощі між СУБД:

1. **Різниця в роботі з типами рядків (`String` / `VARCHAR`):**  
   - У PostgreSQL тип `VARCHAR` без вказання довжини є валідним і необмеженим.  
   - MySQL суворо вимагає явного вказання максимальної довжини рядка (наприклад, `VARCHAR(100)`), інакше створення таблиці падає з синтаксичною помилкою.  
2. **Типи `Boolean` та `Enum`:**  
   - PostgreSQL має нативний тип `BOOLEAN` і підтримує створення користувацьких типів `ENUM` на рівні схеми.  
   - MySQL емулює `BOOLEAN` як `TINYINT(1)` і вимагає обережності при автогенерації типів enum.  
3. **Локалізація повідомлень про помилки підключення (Windows):**  
   - Бібліотека `psycopg2` під час відхилення підключення (невірний пароль чи відсутня база) повертала системне повідомлення в кодуванні Windows-1251, що призводило до `UnicodeDecodeError` у Python замість інформативного опису проблеми. Після налаштування правильних облікових даних зв'язок працював стабільно.
